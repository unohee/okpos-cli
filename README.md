# okpos-cli

OKPOS 영업정보시스템(`okasp.okpos.co.kr`)에 로그인해 **전체 데이터를 수집**하고
Postgres에 적재하거나 xlsx로 내보내는 CLI.

자사 계정으로 접근 가능한 데이터를 대상으로 하며, 요청은 15 RPS 상한 아래에서
사람과 비슷한 간격으로 나갑니다.

## 왜 HTML을 긁지 않는가

조사 결과 이 시스템은 IBSheet 그리드 뒤에 **JSON 엔드포인트**를 두고 있습니다.

```
POST <screen_dir>/ddd.htmlSheetAction
  <TokenKey>=<TokenVal>, S_CONTROLLER, S_METHOD=search,
  SHEETSEQ, S_SAVENAME, S_ORDERBY, + 해당 화면의 조회 조건
→ {"Data": [ ... ], "Result": {"Message": "조회완료", "Code": 0}}
```

따라서 화면 HTML은 **파라미터 이름을 알아내기 위해 화면당 한 번만** 읽고,
실제 데이터 행은 전부 JSON으로 받습니다. 스크래핑이라기보다 비공개 API 호출에
가깝고, 마크업이 바뀌어도 잘 깨지지 않습니다.

수집 대상 목록도 하드코딩하지 않습니다. `/login/menuv.jsp`가 메뉴 전체를
`var AL = [...]` JSON으로 내려주므로 이를 런타임 카탈로그로 사용합니다.
현재 71개 프로그램이며, 벤더가 메뉴를 추가하면 자동으로 따라갑니다.

## 설치

```bash
python3 -m venv ~/dev/venvs/okpos-cli
~/dev/venvs/okpos-cli/bin/pip install -e ".[dev]"
```

`.env.example`을 `.env`로 복사해 채웁니다.

```ini
OKPOS_ID=...
OKPOS_PW=...
OKPOS_URL=https://okasp.okpos.co.kr/login/login_form.jsp
OKPOS_PG_DSN=postgresql://user:pass@localhost:5432/okpos   # 선택
OKPOS_MAX_RPS=15                                           # 선택
```

`.env`는 `.gitignore`에 있습니다. 커밋하지 마십시오.

## 사용법

```bash
okpos check                                   # 로그인·카탈로그·요청 속도 확인
okpos menu --class 매출관리                    # 프로그램 목록
okpos shops                                   # 매장 목록
okpos init-db                                 # Postgres 스키마 생성

okpos scrape --from 2026-08-25                        # 하루치 전체 수집
okpos scrape --from 2026-08-01 --to 2026-08-31        # 기간 수집 (증분)
okpos scrape --from 2026-08-25 --dry-run --no-db      # 조회 계획만 확인
okpos scrape --from 2026-08-25 --class 매출관리 --full  # 특정 분류를 강제 재수집
okpos scrape --from 2026-08-25 --all-shops            # 매장별 화면을 전 매장 순회
okpos scrape --from 2026-08-25 --shop SHOP001          # 매장 하나만

okpos status                                  # 수집 현황
okpos export --from 2026-08-01 --to 2026-08-31 --out exports/aug.xlsx
```

매장 조건이 있는 화면은 매장을 지정해야 데이터가 나옵니다. `--all-shops`는 그런
화면만 골라 전 매장을 순회하고, 매장과 무관한 화면은 한 번만 조회합니다.

기본은 **증분**입니다. 성공 기록이 있는 (컨트롤러, 시트, 매장, 날짜) 조합은
건너뛰므로 매일 크론으로 돌려도 안전합니다. `--full`은 이를 무시합니다.

## 폼 인코딩

페이지는 UTF-8을 선언하고 응답도 UTF-8로 오지만, **서버는 요청 본문을 CP949로
읽습니다.** UTF-8로 보내면 한글이 깨진 채 되돌아옵니다 (`전체` → `??泥?`).

그래서 모든 폼 본문은 `auth.encode_form()`을 거쳐 CP949로 인코딩됩니다.
CP949로 표현할 수 없는 문자는 조용히 `?`가 되는 대신 숫자 문자 참조로 나가
값이 흔적 없이 사라지지 않습니다.

## 요청 페이싱

세 층이 겹쳐 있습니다.

1. **순차 최소 간격** — 15 RPS 하드 상한. 매 요청이 다음 허용 시각을 밀어내는
   방식이라 버스트가 구조적으로 불가능합니다(토큰 버킷이 아닙니다).
2. **lognormal 지터** — 사람이 화면을 넘기는 듯한 간격, 낮은 확률로 더 긴 휴식.
   지터는 **항상 지연을 더하기만** 하므로 상한을 넘길 수 없습니다.
3. **응답시간 적응 감속** — 첫 10개 응답의 중앙값을 그 실행의 정상 기준선으로
   잡습니다. EWMA가 기준선의 3배 이상이면 응답 종료 뒤 추가 간격을 두고(최대 5초),
   1.5배 아래로 회복되면 추가 간격을 20%씩 천천히 줄입니다. 이 층도 요청을
   늦출 뿐 원래 페이스보다 빠르게 만들지 않습니다.

실측 분포는 p50 0.185초 · 평균 0.304초로, 지속 페이스는 약 3.3 RPS입니다.
상한(15 RPS)에 실제로 걸리는 요청은 3.4%뿐이고 나머지는 지터가 정합니다.

`scrape` 실행 후 실측 피크 RPS와 응답시간 기준선·EWMA·적응 감속 횟수 및
최대 추가 간격이 함께 출력됩니다.

## 세션 만료

세션이 끊기면 서버는 JSON 대신 로그인 페이지를 돌려줍니다. 이 경우 클라이언트가
스스로 다시 로그인하고 그 호출을 한 번 재시도하므로, 긴 크롤이 중간부터 조용히
실패하지 않습니다.

재로그인은 CSRF 토큰이 세션에 묶여 있다는 점 때문에 단순한 재시도가 아닙니다.
화면 스펙 캐시에 이전 세션의 토큰이 들어 있으므로 **캐시를 함께 비우고 화면을
다시 읽습니다.** 그러지 않으면 낡은 토큰을 보내 엉뚱한 실패가 납니다.

재로그인 횟수에는 상한(기본 3회)이 있어, 자격증명이 잘못됐을 때 무한히 로그인을
시도하지 않습니다.

## 서버가 바쁠 때

`429`·`503`을 받으면 `Retry-After`를 존중해 기다렸다가 재시도하고, 헤더가 없으면
2→4→8초로 물러섭니다. 3회까지 물러선 뒤에도 같으면 `ServerBusy`로 중단합니다.

다만 **이 서버에서 429는 관측된 적이 없습니다.** 약 1,500회 요청 동안 나온 상태는
`200`과 `404`뿐이고, `Server: Apache`에 rate-limit 헤더도 없습니다. 이 처리는
"오면 대응한다"는 대비이지 관측에 기반한 것이 아닙니다.

느려지는 응답은 적응 감속이 선제 신호로 사용합니다. 다만 **연결 거부·타임아웃처럼
응답 자체가 없는 실패를 연속으로 세어 멈추는 서킷 브레이커는 아직 없습니다.**
그 경로는 실패로 기록되고 크롤이 계속됩니다.

## 데이터 모델

화면마다 컬럼이 14~69개로 제각각이고 벤더가 바꿀 수 있으므로, 물리 컬럼을
고정하는 대신 **메타 컬럼 + JSONB** 하이브리드를 씁니다.

| 테이블 | 용도 |
| --- | --- |
| `okpos.program` | 메뉴 카탈로그 |
| `okpos.record` | 수집된 행 (`payload JSONB` + 메타 컬럼, GIN 인덱스) |
| `okpos.scrape_run` | 조합별 수집 상태 — 증분의 근거 |

`record`는 `(controller, sheet_seq, shop_cd, biz_date, row_no)`가 유니크하므로
재실행은 중복이 아니라 갱신입니다.

xlsx로 내보낼 때는 JSONB를 컨트롤러별 시트의 컬럼으로 다시 펼치므로,
원래 OKPOS 그리드와 비슷한 모양이 됩니다.

## 실측 결과 (2026-08-31, 계정 [ACCOUNT])

각 수치를 낸 명령을 함께 적습니다. 계정·기간이 다르면 값도 달라집니다.

| 항목 | 값 | 재현 명령 |
| --- | --- | --- |
| 카탈로그 | 71개 프로그램 | `okpos menu` |
| 조회 가능 화면 | 70개 (탭 확장 포함) | `okpos scrape --from 2026-08-25 --dry-run --no-db` |
| 매장 | <N>개 (계정별 상이) | `okpos shops` |
| 1일치 (본사 범위) | <조회 수> / <행 수> / <컨트롤러 수> | `okpos scrape --from 2026-08-25` |
| **1일치 전량 (전 매장)** | **<조회 수> / <행 수> / <컨트롤러 수>** | `okpos scrape --from 2026-08-29 --all-shops` |
| 전량 소요 | 환경과 계정 범위에 따라 다름 | 위와 같음 |
| 실측 피크 | 10 RPS (상한 15) | 각 실행이 끝날 때 출력 |
| 재실행 | 전량 스킵, 조회 0 | 같은 명령 재실행 |
| 전량 실행 실패 | 계정과 서버 상태에 따라 다름 | 위와 같음 |

`scrape`는 끝날 때마다 `실측 피크 N RPS`를 출력하므로, 상한 준수는 매 실행이
스스로 증명합니다.

## 알려진 한계

- `sale.cust.day_sale020`(회원포인트실적)은 `code=-9`로 응답합니다. GUI에서도
  데이터가 없는 화면임을 확인했으므로 실질 손실은 없습니다. `scrape_run`에는
  `error`로 남습니다.
- `/sale/day/day_cuprf010.jsp`(컵보증금)는 **404**입니다. 메뉴에는 있는데 파일이
  없는 벤더 쪽 잔재로 보입니다. 권한 문제가 아닙니다.
- 월 단위 화면(`sale.month.*`)은 날짜 입력 필드가 없어 서버 기본값(당월)으로
  조회됩니다. 임의 월을 지정하려면 해당 화면의 파라미터를 따로 다뤄야 합니다.
- 매장 스코프가 필요한 화면은 `--shop` 또는 `--all-shops`가 필요합니다.
  미지정 시 계정 기본 범위로만 조회되며, 영수증별 상세처럼 매장이 필수인 화면은
  0행이 됩니다.
